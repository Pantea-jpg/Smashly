# ADR 0009: Deployment preparation (Phase 10)

- **Status:** Accepted
- **Date:** 2026-11-26
- **Details:** [09 Deployment guide](../09-deployment.md) · [10 Runbooks](../10-runbooks.md) · [11 App Store](../11-app-store.md) · [12 Launch checklist](../12-launch-checklist.md)

## Hosting: Render, Frankfurt (chosen 2026-11-26)

- **Why Render:** the simplest of the three options offered (Render, AWS, Scaleway) for a club without operations staff. It gives:
  - managed PostgreSQL with point-in-time recovery;
  - managed Redis;
  - Docker services with zero-downtime deploys and a pre-deploy step;
  - deploys from GitHub;
  - all of it in the EU.
- **What it does not include:** object storage. Profile pictures go to Cloudflare R2 with EU jurisdiction, through the existing S3 client.
- **Infrastructure as code:** `render.yaml` (a Blueprint with one project and `staging` + `production` environments) is generated by `infra/render/generate-blueprint.mjs`.
  - Plain YAML without anchors, because Render's docs do not say anchors are supported.
  - Plan names are from Render's current Blueprint spec.
- **Secrets:** `sync: false` on each service.
  - Render's docs do not promise that secrets kept in a shared environment group survive a Blueprint sync, so the documented safe pattern is used.
  - The cost: each secret is entered twice per environment (API and worker). The deployment guide lists every one.
- **Production settings:** two API instances (rolling deploys); `autoDeployTrigger: off` (the release workflow decides); and environment protection on.

## One image, three roles

- The API Dockerfile now ships the Prisma CLI (moved to `dependencies`, with `dotenv`), the schema and the migrations.
- The same image runs:
  - **API** (default `CMD`);
  - **worker** (`dockerCommand: node dist/worker.js`);
  - **migrations** (`preDeployCommand: node_modules/.bin/prisma migrate deploy`);
  - **one-off tools:** `node dist/seed.js` for the first admin, and `node dist/verify-restore.js` for restore drills.
- **Version:** `APP_VERSION` falls back to Render's `RENDER_GIT_COMMIT` (first 12 characters), so `/health`, logs and Sentry name the deployed commit.
- **Rehearsed locally with Docker** (throwaway Postgres 17 and Redis on a private network):
  - migrations applied;
  - the API reported ready with the commit version;
  - the worker ran its first jobs;
  - the smoke test passed every check except HTTPS, which Render provides.

## Release pipeline

- **CI (extended):**
  - a **secrets scan** (gitleaks, full history);
  - `pnpm audit --prod --audit-level high`;
  - **image build + migrations applied inside the image** against an empty Postgres.
- **Staging:** Render auto-deploys `main` once checks pass (`checksPass`). `staging-smoke.yml` waits for the new commit on `/health/ready` and runs `scripts/smoke-test.mjs`.
- **Production:** `release.yml` on a `v*.*.*` tag:
  1. reuses the full CI (`workflow_call`);
  2. requires approval (GitHub environment `production`);
  3. calls the API deploy hook with `ref=<sha>` and waits until the API serves that commit (migrations ran first);
  4. only then deploys the worker, so it never runs code ahead of the schema;
  5. smoke-tests production and creates a Sentry release.
- **Smoke test:** read-only, needs no credentials, and safe against production. It checks:
  - liveness, readiness (database and Redis);
  - HTTPS + HSTS;
  - 401 + `no-store` on protected routes;
  - login errors that don't reveal accounts;
  - that unsigned Stripe webhooks are rejected;
  - that API docs are not public.
- **Dependabot:** weekly updates for npm (Expo and Prisma grouped; major Expo/React Native upgrades excluded), GitHub Actions and Docker.

## Monitoring and alerts

- **`core/observability/alerts.ts`:** the one place that reports problems.
  - `alerts.critical(name)` produces a **fatal**, fingerprinted Sentry issue, so one Sentry rule covers every operational alert.
  - `alerts.exception` reports unexpected errors.
  - Everything is also logged, so alerts reach the log stream without Sentry.
- **Alerts:**
  - `reconciliation_mismatch` (worker);
  - `payment_requires_review`;
  - `stripe_webhook_failed` (payments service);
  - `outbox_event_failed` (dispatcher, after the last retry);
  - `outbox_backlog`;
  - unexpected 500s, failed scheduled jobs, unhandled rejections.
- **The backlog is watched by the API**, every 5 minutes on each instance: a stopped worker cannot report itself. Sentry groups duplicate alerts by fingerprint.
- **Privacy:** Sentry 11's `dataCollection` is all off (no user, cookies, headers, query strings or bodies), plus a `beforeSend` scrub. Alert details pass through the log redaction keys (email, token, password …).
- **Required in production:** `SENTRY_DSN` (env validation), EU region.
- **App:** `@sentry/react-native` (8.28, the version Expo SDK 58 pins), initialized in `index.ts` when `EXPO_PUBLIC_SENTRY_DSN` is set, with user, bodies and secret headers stripped.
  - Not yet included: readable stack traces need the Sentry Expo plugin with an auth token at build time. Add it once the Sentry account exists.

## Security carry-overs closed

- **Breached passwords (ASVS 2.1.7):** registration, password reset and password change reject passwords found in Have I Been Pwned.
  - Range API with k-anonymity: only 5 hex characters of the SHA-1 are sent, and padding is requested.
  - New error code `PASSWORD_BREACHED` (422), translated in Dutch and English.
  - **Fails open:** when the service is unreachable the password is accepted and a warning is logged. Registration must not depend on a third party.
  - Can be disabled with `PASSWORD_BREACH_CHECK=false`. A refused reset does not use up the reset link.
- **gitleaks and Dependabot:** in CI (see above).
- **Orphaned profile pictures:** ADR 0003 planned a bucket lifecycle rule on `avatars/`. That would also delete pictures in use, because confirmed and unconfirmed uploads share the prefix. Instead, an hourly worker job deletes pictures under `avatars/` that are older than 24 hours and referenced by no profile (`ObjectStorage.list` added).

## Restore drills

- `verifyRestore(prisma, expectedMigrations)` with `dist/verify-restore.js` checks a restored database:
  - every migration applied, none failed;
  - the append-only and no-delete triggers present;
  - the **full reconciliation** (`run({ persist: false })`, a new option so the check writes nothing);
  - row counts and the newest ledger, audit and sign-in times.
- **Read-only:** enforced by PostgreSQL through `options=-c default_transaction_read_only=on` on every pooled connection, and tested by attempting a write.

## Gap found: no refund screen

- **Found while writing the refund runbook:** the admin app had no way to refund (D17), although the API supported it since Phase 5.
- **Added:** a **Refund** screen (member detail → Refund):
  - cash or card;
  - for a card refund, choose a top-up that still has refundable money, with what is left shown per top-up;
  - the amount is limited to the balance (and to the top-up);
  - a reason, a confirmation dialog, and an idempotency key.
- **Still missing from the app** (documented in the runbooks): an admin list of payments held for review, and a "run reconciliation" button. The dashboard shows both counts, and Sentry alerts carry the details.

## App release

- **Variants:** `app.config.ts` builds **development**, **staging** and **production** variants from `APP_VARIANT` (eas.json). Each has its own name, bundle id (`.dev`, `.staging`) and URL scheme. The app reads its scheme at runtime for email links and Stripe redirects (`shared/config/appScheme.ts`), matching `APP_LINK_BASE` and `APNS_BUNDLE_ID` per environment in `render.yaml`.
- **Privacy manifest:** "required reason" APIs and the collected data types.
- **Export compliance:** declared exempt.
- **Launch screen:** `expo-splash-screen` with light and dark backgrounds.
- **Interim icon:** drawn by `scripts/generate-icons.mjs` (an opaque 1024 × 1024 wallet on the brand blue) until the club's artwork replaces it.

## Verification

- **API:** unit and integration tests for alerts (a fake Sentry transport checks level, fingerprint and scrubbing), env rules, the backlog, alerting on job and payment failures, the breached-password check (k-anonymity, padding, fail-open), registration, reset and change refusals, the orphan picture purge, and the restore check (intact, damaged, read-only).
- **App:** Sentry scrubbing, and the refund screen (cash within the balance, card limited to the chosen top-up, no refundable top-ups).
- **Docker:** the image was built and a full deploy rehearsed with throwaway Postgres 17 and Redis containers: migrations, the first admin via `dist/seed.js` (who then signs in), API and worker, every smoke check except HTTPS, and `verify-restore` reporting `RESTORE OK`.
- **CI:** 768 tests (API 631, app 80, packages 57). Coverage: API 96.1%, app 83.5%.
- **Sizes:**
  - The iOS bundle is 6.8 MB of Hermes bytecode (4.1 MB before); the increase is mostly the Sentry React Native SDK.
  - The server image is 859 MB, mostly the Prisma CLI and engines needed for the pre-deploy migrations.
  - Neither affects request speed. Measure app startup on a device (launch checklist).
- **Not verified here** (needs accounts or a device): everything on Render, Stripe live, APNs, TestFlight, Sentry delivery, the real restore drill. All of it is listed in the launch checklist.
